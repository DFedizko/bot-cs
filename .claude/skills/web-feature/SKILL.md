# Adding a frontend feature

Read `web/ARCHITECTURE.md` and `web/test/CLAUDE.md` first if you haven't. Work test-first: start from a failing UI integration test of the page (step 9) and drive the layers below it with hook and logic tests, all in `web/test/`, mirroring `src/`. Never unit test components.

## 1. Name it

The folder is what the user can do, in kebab-case: `features/wanted-items/`, `features/accounts/`. Check that no existing feature already owns it, and look in `shared/` (`ui/`, `hooks/`, `model/`, `lib/`) before writing anything another feature may already have.

## 2. Model (`model/`)

Types the view works with and the UI rules as plain functions, one per file (`can-save-wanted-item.ts` exports `canSaveWantedItem`). No React, no libraries. Give each rule a plain logic test. Value objects and rules other features also need go to `shared/model/` instead.

## 3. Port (`ports/`)

Only when the feature needs I/O. One interface per role, shaped for this feature (not the API's shape), plus its binding:

```ts
export interface WantedItemsGateway {
    listFor: (accountId: number) => Promise<WantedItem[]>;
}

export const { Provider: WantedItemsGatewayProvider, usePort: useWantedItemsGateway } =
    definePort<WantedItemsGateway>("WantedItemsGateway");
```

## 4. Store (`ports/`), for shared client state

Only for state several components share (selected account, filters, drafts); server state stays in TanStack Query and one component's state in `useState`. Declare the typed store port and its binding:

```ts
export type SelectedAccountStore = Store<SelectedAccount>;

export const { Provider: SelectedAccountStoreProvider, usePort: useSelectedAccountStore } =
    definePort<SelectedAccountStore>("SelectedAccountStore");
```

The view-model reads it with `useStoreState(store, select...)` and changes it with `store.setState(update)`. Never import a state library: the adapter is chosen in `app/` (`createMemoryStore` from `shared/adapters/`).

## 5. Adapter (`adapters/`)

Implements the port with the client from `shared/api` (types generated by `bun run api:types`), mapping the API's types to the model's. Name it after its factory (`create-http-wanted-items-gateway.ts` → `createHttpWantedItemsGateway`). HTTP adapters run for real in the hook and UI tests, against MSW mocks typed by the OpenAPI document (`__mocks__/<endpoint>.mock.ts`). Ports that aren't HTTP (clock, storage, WebSocket) get a fake in `__fakes__/` (`create-fake-clock.ts`).

## 6. View-model (`view-model/`)

`use<Name>ViewModel(...)` gets the port with `use<Port>()`, runs TanStack Query (`queryOptions` factories for reusable queries, keys starting with the feature name) and returns exactly what the view needs: data, UI states, and actions as plain callbacks. Export its return type for the view. Extra custom hooks it needs go in `view-model/hooks/` (or `shared/hooks/` when other features use them too).

Give it a hook integration test: `renderHook` with a wrapper providing a fresh QueryClient without retries, the ports bound to their real adapters (MSW answering) or fakes, and memory stores. Assert the state after each action: initial, loading, success, error.

## 7. View (`view/`)

Components whose props are the view-model's return type (`import type`) or a part of it. Its parts go in `view/components/`; reuse `shared/ui/components/` (and move a part there once another feature needs it). Only local UI state, `shared/ui/components/` and Tailwind, with semantic markup and no needless wrappers. No component test: the page's UI integration test covers them through what the user sees and does.

## 8. Screen and index

- `<feature>.screen.tsx` at the feature root: `const viewModel = useXViewModel(...); return <XView {...viewModel} />;`.
- `index.ts` exports what routes and `app/` need: the screen, the port's `Provider` and interface, and query options for loaders.

## 9. Wire it

- Bind each adapter and store in `app/` by wrapping the app in the ports' `Provider`s.
- Render the screen from a page (`pages/<name>.page.tsx` → `<Name>Page`), and point a route file in `routes/` at that page (`bun run routes` regenerates the route tree).
- Write the page's UI integration test with `renderApp(path)`, the bot's API answered by MSW: what the user sees, what they can do, the requests sent, and each documented error.
- For a main feature, add its happy path to `web/e2e/` (see `web/e2e/CLAUDE.md`).

## 10. Check

`bun run check` in `web/`, and `bun run test:e2e` when you touched a main feature's journey. A boundary error from lint means a dependency points the wrong way: fix the dependency, never the lint config.
